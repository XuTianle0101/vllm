# 逐 Ticket 开发与服务器验证流程

开发已启动，当前 T00 等待服务器验收；后续逐 ticket 执行以下流程。

## 状态与推进规则

状态统一为：`TODO`、`IN_PROGRESS`、`AWAITING_SERVER`、`NEEDS_FIX`、`BLOCKED`、`DONE`。

每次只启动一个 ticket。依赖 ticket 经服务器验收为 DONE 后才能启动下一项。未拿到结果时保持 AWAITING_SERVER；失败留在当前 ticket，修复后重新交付。BLOCKED 必须写明缺少的环境、证据或决策。

## 每轮交付

1. 核验分支、远端、工作区及仓库指令；不覆盖用户改动。
2. 实现当前 ticket，使用 uv 管理环境，按仓库规范运行必要检查。无 GPU 的本地检查不能替代服务器验证。
3. 更新 ticket 的改动说明、实际测试、服务器实验命令和结果预期。同步需要版本化的文档到仓库 `docs/ksa/`。
4. 独立提交或修复提交，push 到 `origin/releases/v0.26.0-ksa`，不 force-push。记录实际 SHA；不自动创建 PR。
5. 交付服务器完整命令：同步并验证 SHA、安装相应环境、运行精度实验、运行性能实验、收集结果。命令必须使用已实现脚本，不给不存在脚本的执行指令。
6. 用户执行并按 [反馈模板](templates/experiment-feedback.md) 返回结果。
7. 分析相对 HF 和上一已验收版本的差异，记录结论。通过则关闭；失败则明确定位下一轮修复与复测范围。

## 基线管理

T00 固定 HF 环境与官方路径、模型哈希、提示集、生成配置和精度容差。参考模型及依赖变更必须形成新的 baseline ID，说明原因并重跑相关比较，不能无记录替换。

精度测试使用固定 token IDs 与教师强制序列，性能测试单独运行，不在计时路径导出大规模 logits。长序列精度导出采用选定位置或流式指标，避免把结果导出造成的显存压力误判为推理 OOM。

并发、缓存和图功能未实现前，相应项目标记 N/A，不声称已经支持。优化 ticket 即使精度通过，若收益没有超过波动，也不能宣称性能提升。

## 每次给用户的交付摘要

- Ticket 与本轮目标。
- 实际分支及推送 SHA，基线 ID。
- 本地已运行检查及结果。
- 服务器需要执行的完整命令与大致测试范围。
- 应返回的结果目录与关键字段。
- 当前限制、预计通过条件和失败时应保留的日志。

## 文档边界

根目录 `docs/` 为本地规划入口。未来版本化副本放入 `vllm/docs/ksa/`，实验脚本放在 vLLM 仓库内。原始实验结果默认保存在服务器并反馈到根目录 `docs/results/`，不默认提交大型 trace、logits 或模型数据。
